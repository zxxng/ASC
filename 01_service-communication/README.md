# 01_service-communication: 서비스 간 통신

## 목표

- 업무에서 쓴 두 가지 연계 방식(동기 Proxy 호출, 이벤트 기반 비동기)을 동작 수준에서 설명할 수 있다
- 각 방식의 실패 상황(지연, 오류, 중복, 순서)에서 무슨 일이 생기는지 테스트로 보여 줄 수 있다
- 상황에 맞는 방식을 고르는 기준을 내 경험으로 설명할 수 있다

## 1회차: 동기 호출

`src/main`의 두 Proxy는 업무에서 본 구조를 **일반화해서 재현한 리뷰 대상**입니다. 정답 코드가 아닙니다.

| 클래스 | 재현한 구조 |
|---|---|
| `RetryBlockingItemProxy` (스타일 A) | 응답 래퍼, retry(3), block(), 호출마다 new ObjectMapper |
| `FallbackItemProxy` (스타일 B) | Map 응답에서 "value" 추출, 토큰 있을 때만 헤더, 실패 시 빈 목록 |

| # | 질문 | 파일 |
|---|---|---|
| Q1 | Proxy를 호출하면 실제로 어떤 HTTP 요청이 나가는가? | `Q1_RequestShapeTest` |
| Q2 | block()은 무엇을 하는가? 블로킹과 논블로킹의 차이는? | `Q2_BlockingTest` |
| Q3 | 상대 서비스가 응답하지 않으면 내 서비스는 어떻게 되는가? | `Q3_TimeoutTest` |
| Q4 | retry(3)은 언제, 몇 번, 어떤 실패에 재시도하는가? | `Q4_RetryTest` |
| Q5 | 실패를 빈 목록으로 바꾸면 호출한 쪽은 구분할 수 있는가? | `Q5_FailureVisibilityTest` |
| Q6 | 호출마다 new ObjectMapper()를 만들어도 괜찮은가? | `Q6_ObjectMapperReuseTest` |
